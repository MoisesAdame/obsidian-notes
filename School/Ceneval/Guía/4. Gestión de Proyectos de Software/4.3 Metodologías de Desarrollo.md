## Ciclo de Vida del Software
### Generalidades
#Q #AOSR/7d73a
- El ciclo de vida del software es el conjunto de **fases** que guían el desarrollo de un :: Sistema de software. #AOSR/7d73a/s/6ckj
- Ayuda a gestionar **costos, tiempo y calidad** en el :: Desarrollo del software. #AOSR/7d73a/s/7lki
- Define el orden en que se realizan :: Actividades y entregables. #AOSR/7d73a/s/5q5s
- Las **7 fases** son :: Planificación, análisis, diseño, implementación, pruebas, despliegue, mantenimiento. #AOSR/7d73a/s/7nr2

### Fases del Ciclo de Vida

#### 1. Planificación
##### Generalidades
#Q #AOSR/1rgsa
- Es la fase donde se **identifican** los :: Objetivos y alcances. #AOSR/1rgsa/s/5ece
- Se estiman los :: Costos, tiempos y recursos. #AOSR/1rgsa/s/36el
- Se realiza un análisis de :: Riesgos. #AOSR/1rgsa/s/21lq

##### Importancia
#Q #AOSR/608me
- Permite evitar :: Problemas futuros. #AOSR/608me/s/2c0q
- Ayuda a definir un **cronograma** con :: Fechas y entregables. #AOSR/608me/s/1di8

#### 2. Análisis de Requisitos
##### Generalidades
#Q #AOSR/24f6e
- Se identifican las **necesidades** del :: Cliente y usuarios. #AOSR/24f6e/s/7p0f
- Se documentan los :: Requisitos funcionales y no funcionales. #AOSR/24f6e/s/z773
- Se usa un **documento** llamado :: Software Requirement Specification (SRS) #AOSR/24f6e/s/7c48

##### Importancia
#Q #AOSR/z2559
- Un mal análisis puede llevar a :: Retrabajos y sobrecostos. #AOSR/z2559/s/28l6
- Se establecen las **bases** del :: Diseño y desarrollo. #AOSR/z2559/s/2idn

#### 3. Diseño
##### Generalidades
#Q #AOSR/4bbnf
- Se definen cosas como la :: Arquitectura. #AOSR/4bbnf/s/3pbj
- Incluye la creación de :: Diagramas y modelos. #AOSR/4bbnf/s/95j9
- Se determinan componentes como :: Base de datos, interfaces. #AOSR/4bbnf/s/4l22

##### Importancia
#Q #AOSR/20dtp
- Un buen diseño reduce :: Problemas en la implementación. #AOSR/20dtp/s/446h
- Permite planificar la :: Escalabilidad y mantenibilidad. #AOSR/20dtp/s/f94s

#### 4. Implementación (Codificación)
##### Generalidades
#Q #AOSR/4j06k
- Se traduce el **diseño** en :: Código. #AOSR/4j06k/s/7prl

#### 5. Pruebas
##### Generalidades
#Q #AOSR/793o1
- Se validan los... y que el software... :: Requerimientos, funcione bien. #AOSR/793o1/s/1gkk
- Se detectan y corrigen :: Errores. #AOSR/793o1/s/20p8

##### Importancia
#Q #AOSR/3i9bp
- Reduce fallos en :: Producción. #AOSR/3i9bp/s/2sto
- Mejora la **confiabilidad** y la :: Experiencia del usuario. #AOSR/3i9bp/s/74ij

#### 6. Despliegue
##### Generalidades
#Q #AOSR/5vtjj
- Es el proceso de poner el software en :: Producción. #AOSR/5vtjj/s/48us
- Puede incluir una fase de **pruebas** en :: Entornos controlados (beta). #AOSR/5vtjj/s/2g1j
- Se realiza la instalación y configuración en :: Servidores o dispositivos.  #AOSR/5vtjj/s/2sv5

#### 7. Mantenimiento
##### Generalidades
#Q #AOSR/fdvec
- Incluye **corrección de errores** y :: Mejoras continuas. #AOSR/fdvec/s/1jqr

##### Importancia
#Q #AOSR/1iu3b
- Hace que el producto :: Tenga una **vida útil** mas larga. #AOSR/1iu3b/s/2otl

## Tabla Comparativa
| **Metodología** | **Tipo** | **Enfoque**                          | **Ventajas**                                       | **Desventajas**                                       | **Cuándo usar?**                                     |
| --------------- | -------- | ------------------------------------ | -------------------------------------------------- | ----------------------------------------------------- | ---------------------------------------------------- |
| **Cascada**     | Clásica  | Secuencial y lineal                  | Claridad y estructura.                             | Cambios costosos, entrega tardía.                     | Requisitos claros, documentación esencial.           |
| **Prototipado** | Clásica  | Iterativa con validaciones tempranas | Mejora la comunicación.                            | Puede requerir rehacer partes.                        | Requisitos inciertos, validación temprana necesaria. |
| **Incremental** | Clásica  | Descomposición en mini proyectos     | Reduce riesgos, entregas parciales.                | Planeación compleja, integración desafiante.          | Proyectos complejos con entregas graduales.          |
| **RAD**         | Clásica  | Desarrollo rápido con iteraciones    | Alta velocidad de entrega.                         | No apto para proyectos grandes, posible baja calidad. | Plazos cortos, UX clave.                             |
| **Concurrente** | Clásica  | Varias fases en paralelo             | Adaptabilidad a cambios, acelera el ciclo de vida. | Difícil de coordinar.                                 | Proyectos modulares, necesidad de velocidad.         |
| **Espiral**     | Clásica  | Combinación de cascada e iteraciones | Mitiga riesgos, integración de cambios continua.   | Costoso, complejo de gestionar.                       | Proyectos grandes con requisitos inciertos.          |
| **Scrum**       | Ágil     | Iterativo e incremental con sprints  | Entregas frecuentes, mejora continua.              | Requiere disciplina, poca documentación.              | Proyectos complejos con cambios frecuentes.          |
| **XP**          | Ágil     | Técnicas de desarrollo extremo       | Código de alta calidad.                            | Solo funciona bien en equipos pequeños.               | Requisitos inestables, alta calidad requerida.       |
| **FDD**         | Ágil     | Desarrollo basado en características | Medición del progreso con features.                | Alta inversión en planificación inicial.              | Equipos experimentados, requisitos claros.           |
| **Kanban**      | Ágil     | Flujo visual y continuo              | Fácil adaptación a cambios.                        | No adecuado para proyectos complejos.                 | Optimización de procesos existentes.                 |
| **Crystal**     | Ágil     | Adaptable según el equipo y proyecto | Flexible y liviano.                                | Ligero para equipos grandes, poca documentación.      | Equipos pequeños y altamente comunicativos.          |
| **ASD**         | Ágil     | Adaptativo en entornos inciertos     | Alta capacidad de respuesta a cambios.             | Falta de estructura, requiere experiencia.            | Innovación, incertidumbre alta.                      |
| **Lean**        | Ágil     | Eliminación de desperdicios          | Reduce costos y tiempos.                           | Menos planificación detallada.                        | Restricciones de recursos, optimización.             |
| **RUP**         | Híbrida  | Basado en iteraciones y UML          | Procesos sólidos, buena gestión de riesgos.        | Burocrático para equipos pequeños.                    | Proyectos y equipos grandes.                         |
| **OpenUP**      | Híbrida  | Versión ligera de RUP                | Menos pesado que RUP, adaptable.                   | Limitado para proyectos muy grandes.                  | Equipos medianos a grandes, colaboración.            |
