## Proceso de la Ingeniería de Requerimientos
### Introducción
#Q #AOSR/6pec3
- Para **iniciar** un proyecto de software hay que identificar :: Una **necesidad** del negocio. #AOSR/6pec3/s/7iju
- Es la disciplina encargada de desarrollar :: Especificaciones maduras. #AOSR/6pec3/s/1pe4
- Las especificaciones maduras, sirven para :: Generar acuerdos entre **stakeholders**. #AOSR/6pec3/s/4ffq
- Las **partes** de la ingeniería de requerimientos son :: Elicitación, especificación, validación y administración. #AOSR/6pec3/s/44o3
- Nos da el mecanismo para entender :: Lo que **quiere** el cliente. #AOSR/6pec3/s/2p8s
- Es un proceso :: Iterativo. #AOSR/6pec3/s/6gk8

- Tiene 4 partes que son :: Concepción, indagación, análisis de requerimientos y negociación. #AOSR/m4ogt/s/48q8

- En esta etapa, también se identifican los requerimientos de :: Usuario y sistema. #AOSR/4thhc/s/4qa3

##### 1.4 Negociación

#### 3 Validación
##### Introducción
#Q  #AOSR/7vnie
- Consiste en volver a :: Revisar requerimientos. #AOSR/7vnie/s/bis5
- Se revisan los requerimientos para ver que no haya :: Ambigüedades, inconsistencias u omisiones. #AOSR/7vnie/s/1rce
- En esta fase esta involucrado :: Todo el equipo. #AOSR/7vnie/s/7ord
- Al terminar la fase, el usuario tiene que :: Firmar. #AOSR/7vnie/s/4g1k
- Ve que los requerimientos sean suficientes para **cumplir** las :: Necesidades de los usuarios. #AOSR/7vnie/s/5uvv
- Este proceso se hace antes del :: Diseño y desarrollo. #AOSR/7vnie/s/1lig
- Estas actividades se **encargan** de... y... cualquier requerimiento innecesario o incorrecto :: Detectar, corregir. #AOSR/7vnie/s/3mng

###### Checklists

### User Stories
#### Introducción
#Q  #AOSR/7db9o
- Son una pequeña pieza del... que un... puede entregar en una... :: Valor de negocio, desarrollador, iteración. #AOSR/7db9o/s/2rl4
- La historia de usuario **no es una** :: Función. #AOSR/7db9o/s/4oh2
- Es una **explicación** de una... desde la perspectiva del... :: Función, usuario. #AOSR/7db9o/s/5vub
- **Estructura** de una historia de usuario :: Como un *(tipo de usuario)*, quiero *(acción/feature)* de tal forma que *(pueda lograr tal objetivo/beneficio)*. #AOSR/7db9o/s/3o10
- Los **criterios de aceptación** de una user story son las condiciones que nos permiten decir si la historia de usuario está :: Completa o no. #AOSR/7db9o/s/fn34
- Generalmente, para **medirlas** se usan los :: Story points. #AOSR/7db9o/s/15hi
- Los **story points** de una user story son una forma de estimar cosas como :: Complejidad, esfuerzo y tiempo. #AOSR/7db9o/s/2s9d

#### Características de una Buena User Story
#Q  #AOSR/73kuq
- Las buenas user stories usan el modelo :: INVEST. #AOSR/73kuq/s/5n0l
- El modelo **INVEST** considera que las historias sean :: Independent, negotiable, valuable, estimable, small y testable. #AOSR/73kuq/s/7jnl
- **Independent** es que no dependa de :: Otras user stories. #AOSR/73kuq/s/1uki
- **Negotiable** es que pueda... y... :: Cambiar, discutirse. #AOSR/73kuq/s/1odp
- **Valuable** le de valor al :: Usuario. #AOSR/73kuq/s/7bh5
- **Estimable** es que se pueda estimar su :: Tamaño. #AOSR/73kuq/s/gtlv
- **Small** es que debe entrar dentro de una :: Iteración. #AOSR/73kuq/s/1cm9
- **Testable** es que de la info necesaria para :: Probarla. #AOSR/73kuq/s/2hhs
