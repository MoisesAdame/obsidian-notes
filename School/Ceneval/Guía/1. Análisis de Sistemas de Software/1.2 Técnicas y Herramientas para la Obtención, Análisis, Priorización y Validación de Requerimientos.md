### User Stories
#### Introducción
#Q 
- Son una pequeña pieza del... que un... puede entregar en una... :: Valor de negocio, iteración.
- La historia de usuario **no es una** :: Función.
- Es una **explicación** de una... desde la perspectiva del... :: Función, usuario.
- **Estructura** de una historia de usuario :: Como un *(tipo de usuario)*, quiero *(acción/feature)* de tal forma que *(pueda lograr tal objetivo/beneficio)*.
- Los **criterios de aceptación** de una user story son las condiciones que nos permiten decir si la historia de usuario está :: Completa o no.
- Generalmente, para **medirlas** se usan los :: Story points.
- Los **story points** de una user story son una forma de estimar cosas como :: Complejidad, esfuerzo y tiempo.

#### Características de una Buena User Story
#Q 
- Las buenas user stories usan el modelo :: INVEST.
- El modelo **INVEST** considera que las historias sean :: Independent, negotiable, valuable, estimable, small y testable.
- **Independent** es que no dependa de :: Otras user stories.
- **Negotiable** es que pueda... y... :: Cambiar, discutirse.
- **Valuable** le de valor al :: Usuario.
- **Estimable** es que se pueda estimar su :: Tamaño.
- **Small** es que debe entrar dentro de una :: Iteración.
- **Testable** es que de la info necesaria para :: Probarla.

#Q 
- Consiste en **observar** a los usuarios en :: Su entrono natural de trabajo.
- Observarlos en su entorno natural nos sirve para ver como... con los sistemas o procesos y así detectar sus... :: Interactúan, necesidades.

### Perfiles de los Stakeholders - Personas
#Q 
- Una de las primeras cosas al desarrollar software es **identificar** :: A tus usuarios.
- **Identificar a los usuarios** sirve para hacer funciones que les sean... y diseñar una... adecuada :: Útiles, interfaz.
- En esta técnica se describen a los... como... :: Actores, gente real (con familia, gustos, experiencia laboral, etc.)
- Ver a los actores como gente real, sirve para que los desarrolladores tenfan una... de los usuarios. Visión compartida.
- Esta técnica nos ayuda a **imaginar** lo que los usuarios... y también nos ayuda a ver las... de su uso. Quieren, dificultades.
- Al final esta técnica sirve para... con el usuario :: Empatizar.

## 3 Priorización y Negociación de Requerimientos
#Q 
- Sirve para **centrarse** en cosas :: Importantes del sistema.
- Tiene el fin de **cumplir** con las :: Expectativas de usuario.
- Se logra dándole... a los requerimientos entre sí :: Jerarquía.
- Es necesario que los **stakeholders** entiendan los... de sus requerimientos para que hagan **decisiones**... sobre cuales requerimientos... :: Trade-offs, inteligentes, implementar.
- Hay dos formas de priorizar los requerimientos :: La forma *simple* (Método MoSCoW) o basándose en *valor, costo y riesgo*.
- El método **MoSCoW** tiene 4 categorías de requerimientos :: **M**ust have, **S**hould have, **Co**uld have y **W**on't have (but maybe in the future.)

## 4 Validación de los requerimientos
### Introducción
#Q 
- Ve que los requerimientos sean suficientes para **cumplir** las :: Necesidades de los usuarios.
- Este proceso se hace antes del :: Diseño y desarrollo.
- Estas actividades se **encargan** de... y... cualquier requerimiento innecesario o incorrecto :: Detectar, corregir.

### Técnicas
#### Generación de Casos Prueba
#Q 
- El requerimiento debe poderse :: Testear.
- Si el requerimiento es **difícil** de testear, es que seguramente el requerimiento será :: **Difícil** de implementar.

#### Prototipado
#Q 
- Se le presenta el prototipo al :: Usuario final o cliente.
- Con el fin de obtener :: Feedback.

#### Review de Requerimientos
#Q 
- En esta técnica se checa el :: Documento de especificación de requerimientos (SRS).
- Se hace por un subconjunto :: De los **stakeholders**.
- Todo el tiempo se busca que los requerimientos no tengan... ni.. :: Errores, ambigüedades

#### Checklists
#Q 
- Para cada requerimiento checa aspectos como :: Completitud, claridad y viabilidad.
