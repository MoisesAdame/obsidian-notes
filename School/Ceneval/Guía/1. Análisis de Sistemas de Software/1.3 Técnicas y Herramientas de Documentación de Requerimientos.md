## Introducción
### Necesidad
#Q 
- Los requerimientos se definen para facilitar la **estimación** de cosas como :: Costo, tiempo y si subcontratar o no.
- El SRS le **dice** a los programadores las... para su sistema :: Expectativas.
- Es útil incluso si no se tiene :: Conocimiento técnico.
- Para definir bien los requerimientos nos apoyamos del **estándar** :: IEEE STD 830-1998
- El IEEE 830 le sirve a :: Usuario, cliente y desarrollador.
- El propósito del IEEE 830 es ayudarnos a hacer el :: Software Requirement Specification.

### Definiciones
#Q 
- El **contrato** es un documento legalmente... al que todas las partes deben estar... :: Obligatorio, de acuerdo.
- En el **contrato** es especifican requisitos... y requerimientos de la... así como cosas como... y... :: Técnicos, organización, costo, tiempo.
- El **cliente** es quien... y quien generalmente define... :: Paga, requerimientos.
- **Proveedor** es quien genera un... para un... :: Producto, cliente
- El **usuario** es quien opera... :: El producto.

## Consideraciones para Producir un Buen SRS
### Naturaleza del SRS
#Q 
- El SRS se puede **escribir** por una o más personas ya sea del lado de :: Proveedor, cliente o ambas.
- La **funcionalidad** es :: Que hará el software.
- Las **interfaces externas** es como actúa el sw. con :: Gente, hardware u otro sw.

### Ambiente del SRS
#Q 
- Hay dos posibilidades para el sw. que desarrollemos, **primero** que contenga... y **segundo** que sea una parte de un... :: Toda la funcionalidad, sistema más grande.
- Si el **sw. es parte de un sistema más grande**, hay que especificar en el SRS las... entre ambos sistemas :: Interfaces

### Características de un Buen SRS
#Q 
- Son **8 características** que son (CICMCDCI) :: Correcto, inequívoco, completo, consistente, delinear (con importancia y/o estabilidad), comprobable, modificable, identificable.
- Es **correcto** si cada requisito declarado :: Está en el sw.
- Es **inequívoco** si cada requisito tiene una sola :: Interpretación.
- Es **completo** si todos los... están relacionados a la funcionalidad, el desarrollo, las restricciones del diseño, los atributos y las interfaces externas.
- Es **completo** si todas las... del sw. tienen una respuesta... :: Entradas, definida.
- Es **consistente** si ningún subconjunto de requerimientos perteneciente al SRS genera entre sí :: Conflictos.
- **Delinea** la importancia y/o estabilidad a través de... en cada... :: Identificadores, requisito.
- Es **comprobable** si cada requisito es..., cada requisito es comprobable si existe un método... y... para comprobarlo. :: Comprobable, rentable, finito
- Es **modificable** si se le pueden hacer cambios de forma fácil y consistente a cosas como los :: Requisitos, estructura y estillo.
- Es **identificable** si se puede identificar el... y las... de cada requisito. :: Origen, referencias.

### Preparación de los JOIN del SRS
#Q 
- El SRS debe ser realizado en **conjunto** por el :: Proveedor y el cliente.
- El SRS se escribe en conjunto porque el **cliente no sabe**... y el **proveedor no entiende**... :: Desarrollar sw., el problema.

### Evolución de SRS
#Q 
- El SRS **evoluciona** porque es imposible diseñar todo el sistema desde :: El inicio.
- Los cambios al SRS se dan cuando se encuentran :: Deficiencias.
- Para **generar estos cambios** hay que llevar a cabo un proceso de :: Cambio Formal.
- El **proceso de cambios formal** nos permite tener un... y deja una... :: Control, huella.
- Todo **cambio aprobado** debe :: Incorporarse al SRS.

## Partes de un SRS
#Q 
- Las **3 secciones principales** de un SRS son :: Introducción, descripción general y requerimientos específicos.

### 1 Introducción
#Q 
- Nos da una descripción... del SRS :: General.
- Las **5 subsecciones** que tiene son :: Propósito, alcance, acrónimos y abreviaturas, referencias y descripción general del documento.

#### 1.1 Propósito
#Q 
- Nos dice el :: Público objetivo.
- Nos dice el propósito del :: SRS.

#### 1.2 Alcance
#Q 
- Identificar el... de sw. que se desarrollará :: Tipo (Generador de Reportes, Host DBMS, etc.)
- Describir lo que el sw. ... y lo que... :: Hará, no hará.
- También se habla de cosas como... ,... y... que se planea obtener con el sw. :: Beneficios, objetivos, metas.

#### 1.3 Definiciones, siglas y abreviaciones
#Q 
- Todos los términos, acrónimos y abreviaturas **pertinentes** se deben :: Definir.

#### 1.4 Referencias
#Q 
- Dar una... completa de todos los documentos... en el SRS :: Lista, usados.

#### 1.5 Descripción General u Apreciación Global
#Q 
- Del documento explica como está :: Organizado.
- Describe lo que contienen las secciones :: Restantes del SRS.
- También nos explica que contienen las :: Otras secciones del documento.
### 2 Descripción General
#Q 
- Generalmente tiene **subsecciones** tales como :: Perspectiva del producto, funciones del producto, características del usuario, restricciones y suposiciones y dependencias.
- No especifica los :: Requerimientos
- De los requerimientos, da una descripción de :: Alto nivel.

#### 2.1 Perspectiva del Software
#Q 
- Se describen todas las... dentro de las cuales debe funcionar el software :: Condiciones.
- Tiene muchas subsecciones de cosas como :: Interfaces (sistema, usuario, hardware, etc.)
- Se especifican cosas como las restricciones de :: Memoria.

#### 2.2 Funciones del Software
#Q 
- Resumen de las principales :: Funcionalidades del sw.
- Las funciones descritas las debe poder :: Entender quien sea.
- Los **métodos** que se pueden usar para describir las funciones pueden ser :: Textuales o gráficos.

#### 2.3 Características de los Usuarios
#Q 
- Se deben especificar aspectos de los usuarios como :: Nivel educativo, experiencia profesional y capacidades técnicas.
- Nos sirve para entender la **razón de ser** de los :: Requerimientos.
- Hay que detectar que tan capaz es cada usuario de **influir** en el proyecto y con base en ello, hacer una :: Estrategia de atención.

#### 2.4 Restricciones
#Q 
- Es todo aquello que al desarrollo lo :: Limita
- Son cosas como :: Leyes, hardware, seguridad, etc.

#### 2.5 Suposiciones y Dependencias
#Q 
- Se enlistan todos los... que... a los requerimientos :: Factores, afectan
- Los factores son todos aquellos **aspectos que si cambian** provocan :: Cambios en los requerimientos.

#### 2.6 Priorización de Requerimientos
#Q 
- Dice que requerimientos se deben atender... y cuales se pueden... :: Primero, posponer.

### 3 Requerimientos Específicos
#Q 
- En esta parte se establecen **todos** los :: Requisitos del software.
- Los requisitos de sw. debe estar a detalle para que los **analistas** lo puedan... y los **auditores** lo puedan... :: Diseñar, probar.

#### 3.1 BPMN "To be"
#Q 
- BPM busca mejorar el... y... **procesos** :: Desempeño, optimizar
- Al aumentar la eficiencia de los procesos logramos la :: Satisfacción del cliente.
- Un **proceso de negocio** es una serie... de... :: Discreta, actividades.
- El **to be** es la forma en que el proceso de negocio :: Debería ser.
- El objetivo de **BPMN** es hacer los procesos de negocio fáciles de :: Leer y entender.

#### 3.2 Interfaces Externas
#Q 
- De forma **detallada debe describir** todas las... y... del sistema :: Entradas, salidas.
- **Complementa** a la sección :: 2.1 Perspectiva del sw.
- De cada interfaz se deben registrar cosas como :: Nombre, fuente de entrada o salida, rangos válidos, formatos, etc.
- Ejemplos son :: Interfaces gráficas, formatos de archivos.

#### 3.2 Funciones
#Q 
- Se describe del sw. las :: Acciones fundamentales.
- A grandes rasgos aquí se especifican los requerimientos :: Funcionales.
- Es apropiado dividir los requerimientos funcionales en :: Subfunciones o subprocesos.

#### 3.3 Requisitos de Desempeño
#Q
- Se deben especificar **requerimientos** de tipo :: Estático y dinámico.
- Los requerimientos **estáticos** son los que :: Casi no cambian (arquitectura, hardware)
- Los requerimientos **dinámicos** son los que :: Todo el tiempo cambian, debido a factores ambientales (cantidad de datos a procesar.)

#### 3.4 Requisitos Lógicos de Base de Datos
#Q 
- Se deben especificar aspectos **logicos** tales como :: Tipo de información, frecuencia de uso, entidades y relaciones, restricciones de integridad.

#### 3.5 Restricciones de Diseño
#Q 
- Restricciones impuestas por cosas como :: Estándares o limitaciones de hardware.

#### 3.6 Atributos de Calidad de Software
#Q 
- Se detallan los atributos de... o también conocidos como las... :: Calidad, "ilities" 
- Son una especie de requerimientos de tipo :: No funcional.
- Deben de escribirse de tal forma que puedan ser **verificados** de forma :: Objetiva.
- Algunos de ellos son :: Fiabilidad, disponibilidad, seguridad, mantenimiento y portabilidad.
- La diferencia entre **fiabilidad** y **disponibilidad** es que :: Fiabilidad es que funcione bien, disponibilidad es que "no se caiga".
- La **portabilidad** es que tan fácil es poner el sw. en otro :: Servidor.

#### 3.7 Organización de Requerimientos Específicos
#Q 
- Se deben **organizar** los requerimientos de tal forma que sean :: Fáciles de entender.
